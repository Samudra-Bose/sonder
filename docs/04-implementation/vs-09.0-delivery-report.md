## 1. Executive Summary

Milestone **VS-09.0** establishes the definitive, canonical frontend feature completion inventory and engineering backlog for Sonder, resolving prior inventory accounting ambiguities across the Master Specification (`Community-Work-Management-Master-Specification-v1.5.0.md`) and Master PRD (`Community-Work-Management-v1.5/docs/01-product/master-prd.md`).

This milestone:
1. Reconciles all **70 canonical `FEAT-` patterns** into an unambiguous 1-to-1 classification.
2. Evaluates the **53 actionable concrete capabilities** across seven mutually exclusive status categories.
3. Formally delineates **provisional frontend candidate coverage** (operating against local MSW mock fixtures in Vitest) from **live backend production acceptance** (database ACID guarantees, production rate limits, PITR backups, auth services, and live WebSocket transport).
4. Eradicates obsolete Jira-derived **Project** and **List** container entities, establishing the strict canonical hierarchy:
   $$\text{Community} \longrightarrow \text{Workspace} \longrightarrow \text{Task} \longrightarrow \text{Subtask}$$

6. 7. Sequences the remaining 10 Phase 1 capabilities into an 8-milestone backend-independent engineering backlog (**Inventory A**) using existing candidate OpenAPI 0.3.20-draft schemas and MSW mocks.
8. Reaffirms that **UI/UX Track B** remains strictly **PAUSED** until Phase 1 backend-independent functional features are completed and locked.

## 3. Frontend Scope vs. Live Backend & Operational Acceptance

A foundational governance requirement locked in this audit is the explicit separation between **frontend candidate completion** and **live backend acceptance**:

1. **Provisional Frontend Candidate Scope:**
   Capabilities marked as **DONE** represent verified React components, hooks, state machines, and MSW handlers executing in `apps/web/`. Passing unit and integration tests confirms client rendering, local state management, optimistic updates, and mock API conformance.
2. **Backend & Infrastructure Boundaries:**
   Passing frontend tests does **NOT** certify live backend availability, PostgreSQL ACID transaction guarantees, production edge rate limiting, server backup/PITR recovery drills, or operational compliance.
3. **`FEAT-J03` Specific Separation:**
   - **Frontend Verified:** Accessible design system primitives, CSS token variables in `@theme`, WCAG 2.2 AA contrast ratios ($\ge$ 4.5:1), semantic `.focus-ring` tokens, keyboard navigation, theme provider resolution, and reduced-motion listeners.
   - **Operational Platform Gates Pending:** Edge rate limits, server backup/PITR restore drills, security hardening, and production disaster recovery rehearsals remain distinct platform engineering gates pending backend infrastructure deployment.
4. **`FEAT-G01`, `FEAT-A04`, `FEAT-F01a` Specific Separation:**
   - Client-side authentication (`FEAT-G01`), threaded collaboration (`FEAT-A04`), and notification inbox (`FEAT-F01a`) operate against MSW mock handlers.
   - Live backend identity providers, production cookie domain routing, cross-session watcher database persistence (`DEP-COLLAB-01`), live WebSocket gateway (`DEP-REALTIME-01`), and transactional notification outboxes remain pending backend engineering milestones.

## 4. Canonical Hierarchy & Entity Model

The canonical platform hierarchy is strictly:
$$\text{Community} \longrightarrow \text{Workspace} \longrightarrow \text{Task} \longrightarrow \text{Subtask}$$

- **Elimination of "Projects" and "Lists":**
  "Projects" and "Lists" (as intermediate container entities between Workspace and Task) were obsolete artifacts from earlier Jira competitive analysis and have been completely eradicated from domain schemas, contracts, and documentation.
- **Workspace-Level Functionality:**
  Legitimate management capabilities operate strictly at the **Workspace** level:
  - `FEAT-E01`: Workspace Overview & Workload Summary (formerly Project Overview)
  - `FEAT-D05a` / `FEAT-D05b`: Workspace Starter & Configuration Templates (formerly Project Templates)
  - `FEAT-I01`: Workspace-Scoped Intake Forms (formerly Project Intake Forms)
- **Presentation Layout Clarification:**
  "List View" refers strictly to one of the four presentation view modes (`TaskListView.tsx`), not a container entity in the data model.
